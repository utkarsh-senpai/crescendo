# Crescendo v2.0 Implementation Plan

- **Branch:** `feature/v2.0-real-data-ml` (off `develop`)
- **Status:** Active build
- **Date:** 2026-08-20
- **Owner:** utkarsh-senpai

This document is the developer reference for the v2.0 release. It covers the data architecture
that motivates v2.0, a feature-by-feature breakdown with exact file paths and required changes,
and the deployment + rollback plan.

---

## 1. Background and motivation

As of v1.7.0, the game runs on synthetic momentum features. The prediction engine exists, the
real-data collection infrastructure exists, and the config flag to switch between synthetic and
real momentum exists (`crescendo.game.use-real-momentum`, default `false`). v2.0 is the release
that wires everything together and flips that switch.

Alongside the data flip, v2.0 bundles the ML-stack upgrades that were deferred until real data
was available: an Isolation Forest inorganic detector, multi-horizon predictions, AI archetypes,
and a model registry for reproducibility. All are bundled in the single v2.0 PR because they
share the same dependency on the expanded Neon dataset.

## 2. Data architecture

### 2.1 Two data pools

The system has two distinct artist populations. Understanding the boundary between them is
essential to understanding v2.0.

**Pool 1 — ML emerging artist pool**

Table: `tracked_artist` (Neon Postgres)
Purpose: training data for the organic-breakout prediction model
Contents: 43 small electronic channels (4Tune, DEAF KEV, Chime, ROY KNOX, etc.)
Subscriber band: 1k–100k at entry (the v0.1 seed criterion)
Populated by: `crescendo seed-genres` when run with the original `ml/seeds/electronic_playlists.txt`
Collecting since: 2026-08-18 (real data); 2026-05-01 to 2026-08-17 is synthetic backfill
Real snapshot count as of 2026-09-15: 1,247 (43 artists × 29 days, all runs 43/43 succeeded)

**Pool 2 — Game demo roster**

Source file: `ml/seeds/genre_artists.txt` (format: `GENRE|channel_id|Name`)
Purpose: the game board artists players draft
Contents: 55 top-artist/top-label channels (20 POP / 18 EDM / 17 BOLLYWOOD)
Examples: Fred again.., AP Dhillon, T-Series, Blackpink
Populated by: `crescendo seed-genres` (idempotent, no sub-band filter)
Neon status before v2.0: NOT in Neon — these artists are seeded only in the Spring Boot H2/Neon
game DB via `DataSeeder`, not in the ML `tracked_artist` table

The game currently scores Pool 2 artists on synthetic snapshots generated by `DataSeeder`. Real
momentum features for Pool 2 will only exist after `collect.yml` runs on main post-merge.

### 2.2 Neon schema (relevant tables)

`tracked_artist` — artists being monitored by the cron
```
artist_id       BIGSERIAL PRIMARY KEY
channel_id      TEXT NOT NULL UNIQUE
name            TEXT NOT NULL
genre           TEXT
entry_subs      BIGINT
created_at      TIMESTAMPTZ DEFAULT now()
```

`daily_snapshot` — one row per artist per day
```
snapshot_id     BIGSERIAL PRIMARY KEY
artist_id       BIGINT REFERENCES tracked_artist
snapshot_date   DATE NOT NULL
subscriber_count BIGINT
view_count      BIGINT
video_count     INT
collected_at    TIMESTAMPTZ DEFAULT now()
UNIQUE (artist_id, snapshot_date)
```

`dataset` — feature-engineered rows written by `crescendo build-dataset`; one row per
(artist, as-of-date, dataset version)
```
dataset_id      BIGSERIAL PRIMARY KEY
artist_id       BIGINT REFERENCES tracked_artist
as_of_date      DATE NOT NULL
dataset_version TEXT NOT NULL
growth_7d       FLOAT
growth_30d      FLOAT
subs_accel_7d   FLOAT
views_accel_7d  FLOAT
inorganic_score FLOAT
suspected_inorganic BOOLEAN
breakout_label  BOOLEAN
prediction_interval_lo FLOAT
prediction_interval_hi FLOAT
confidence_tier TEXT
created_at      TIMESTAMPTZ DEFAULT now()
```

`model_registry` — new in v2.0; see Feature F

`collect_run` — audit log of every cron execution; written by `crescendo collect`

### 2.3 How the Spring game reads from Neon

The existing seam works as follows. `GameService.realMomentum(artistId, asOfDate)` (in
`backend/src/main/java/io/crescendo/game/service/GameService.java`) is a stub that returns
synthetic data when `crescendo.game.use-real-momentum=false`. v2.0 builds a real implementation
by adding a `RealMomentumService` that queries the Neon `dataset` table via JDBC.

The Spring Boot game's Neon connection is configured via the `spring.datasource` properties in
`backend/src/main/resources/application-prod.properties` using the `DATABASE_URL` environment
variable already set as a Render secret.

## 3. Feature A — Seed Neon with game pool artists and start daily collection

and manually trigger the `collect.yml` workflow once. The daily cron (04:00 UTC) will continue
from that point autonomously.

Do not flip `crescendo.game.use-real-momentum` at this stage. Wait for data accumulation
(see deployment checklist in §8).

Confirm that all 55 game artists appear in `tracked_artist` and the latest `collect_run` row

## 4. Feature B — Real momentum switch (`RealMomentumService`)

### File to create

`backend/src/main/java/io/crescendo/game/service/RealMomentumService.java`

This service holds one public method:

```java
public Optional<ArtistFeatureSnapshot> fetchForArtist(long artistId, LocalDate asOfDate)
```

Implementation: query the Neon `dataset` table using the existing Spring JDBC template (or
`JdbcTemplate` injected via the existing datasource bean). The query is:

```sql
SELECT *
FROM dataset
WHERE artist_id = :artistId
  AND as_of_date = :asOfDate
ORDER BY dataset_version DESC
LIMIT 1
```

Return an `Optional<ArtistFeatureSnapshot>` mapped from the result row. If no row exists,
return `Optional.empty()` — the caller falls back to synthetic.

### File to modify

`backend/src/main/java/io/crescendo/game/service/GameService.java`

The existing `realMomentum()` method stub returns synthetic data unconditionally. Replace its
body with:

```java
if (useRealMomentum) {
    return realMomentumService.fetchForArtist(artistId, asOfDate)
        .orElse(syntheticSnapshot(artistId, asOfDate));
}
return syntheticSnapshot(artistId, asOfDate);
```

Inject `RealMomentumService` via constructor injection and bind `useRealMomentum` from the
`@Value("${crescendo.game.use-real-momentum:false}")` annotation already present.

### Configuration

`backend/src/main/resources/application.properties` already contains:
```
crescendo.game.use-real-momentum=false
```

To flip to real momentum in production, set the environment variable in the Render dashboard:
```
CRESCENDO_GAME_USE_REAL_MOMENTUM=true
```
This overrides the default without a code change or redeploy (Render restarts the service on
env var changes).

### Tests to add

`backend/src/test/java/io/crescendo/game/service/RealMomentumServiceTest.java`
- Test that a matching dataset row is returned as a correctly mapped `ArtistFeatureSnapshot`
- Test that `Optional.empty()` is returned when no row matches
- Test that `GameService.realMomentum()` falls back to synthetic when the service returns empty

## 5. Feature C — Isolation Forest inorganic detector

### File to modify

`ml/src/crescendo/features.py`

The existing inorganic detector uses a weighted heuristic blend of growth-velocity outlier
scores. Replace this with a scikit-learn `IsolationForest` trained per artist on a rolling
window of four features: `subs_delta`, `views_delta`, `video_count_delta`, and
`subs_views_ratio_change`.

### Design

Training:

```python
from sklearn.ensemble import IsolationForest
import numpy as np

def fit_inorganic_detector(history_df: pd.DataFrame) -> IsolationForest | None:
    """Fit a detector on the first 14 days of an artist's history.
    Returns None if fewer than 14 days are available (caller uses heuristic fallback).
    """
    clean = history_df.head(14)
    if len(clean) < 14:
        return None
    X = clean[["subs_delta", "views_delta", "video_count_delta", "subs_views_ratio_change"]].values
    model = IsolationForest(contamination=0.1, random_state=42)
    model.fit(X)
    return model
```

Scoring:

```python
def score_inorganic(row: pd.Series, detector: IsolationForest | None) -> float:
    """Returns inorganic_score in [0, 1]. Higher = more suspicious."""
    if detector is None:
        return _heuristic_inorganic_score(row)  # keep old logic as fallback
    x = row[["subs_delta", "views_delta", "video_count_delta", "subs_views_ratio_change"]].values.reshape(1, -1)
    raw = detector.decision_function(x)[0]  # negative = more anomalous
    # Normalize to [0, 1]: decision_function range is typically [-0.5, 0.5]
    score = float(np.clip(0.5 - raw, 0.0, 1.0))
    return score
```

The `suspected_inorganic` boolean threshold stays at `inorganic_score >= 0.6`.

### Evaluation addition

`ml/src/crescendo/evaluate.py`

Add a `detector_auc` metric to `EvalResult`. Generate a synthetic contaminated dataset where
known "pumped" rows (subs_delta multiplied by 5–10x over one day) are labeled as inorganic
ground truth, then compute AUC of the `inorganic_score` against those labels. This produces
a defensible "the detector works" number separate from the main precision@k metric.

The existing 22 pytest tests for features must continue to pass. Add tests in
`ml/tests/test_features.py` covering:
- Isolation Forest path returns a score when 14+ days history is present
- Heuristic fallback activates for <14 days history
- Pumped rows score higher than clean rows on the synthetic fixture

## 7. Feature E — AI archetypes

### File to modify

`backend/src/main/java/io/crescendo/game/service/OpponentDrafter.java`

Add an `ArchetypeStrategy` enum to the same package:

```java
public enum ArchetypeStrategy {
    QUANT,        // maximises expected breakout_score
    CONTRARIAN,   // maximises discovery_edge
    RISK_MANAGER  // maximises breakout_score / uncertainty_width
}
```

Modify `OpponentDrafter` constructor to accept an `ArchetypeStrategy`. The drafting logic
switches on strategy to select the utility function applied per candidate artist:

```java
private double utility(ArtistScore score, ArchetypeStrategy strategy) {
    return switch (strategy) {
        case QUANT        -> score.getBreakoutScore();
        case CONTRARIAN   -> score.getDiscoveryEdge();
        case RISK_MANAGER -> {
            double width = score.getPredictionIntervalHi() - score.getPredictionIntervalLo();
            yield width > 0.0 ? score.getBreakoutScore() / width : score.getBreakoutScore();
        }
    };
}
```

The bounded DFS that enforces the salary cap (existing logic) is unchanged; only the per-artist
value function is swapped.

### File to modify

`backend/src/main/java/io/crescendo/game/service/GameService.java`

on `POST /api/games` if the frontend exposes a picker). Store the selected archetype name as a

### File to modify

## 8. Feature F — Model registry and reproducibility

### Schema addition

Add to the ML Postgres schema (`ml/src/crescendo/db.py`, `crescendo status` DDL):

```sql
CREATE TABLE IF NOT EXISTS model_registry (
    registry_id           BIGSERIAL PRIMARY KEY,
    version               TEXT NOT NULL UNIQUE,
    training_window_start DATE NOT NULL,
    training_window_end   DATE NOT NULL,
    feature_count         INT NOT NULL,
    precision_at_k        FLOAT,
    organic_precision_at_k FLOAT,
    brier_score           FLOAT,
    ece                   FLOAT,
    created_at            TIMESTAMPTZ DEFAULT now()
);
```

### Files to modify

`ml/src/crescendo/model.py` — `CrescendoModel.save()` and `MultiHorizonModel.save()`:
after writing the `.pkl` artifact, insert a row into `model_registry` with the version string,
training window, and feature count. Metrics are initially NULL; `crescendo evaluate` fills them.

`ml/src/crescendo/evaluate.py` — after computing metrics, update the matching `model_registry`
row: `UPDATE model_registry SET precision_at_k=?, organic_precision_at_k=?, brier_score=?,
ece=? WHERE version=?`.

### CLI additions

`ml/src/crescendo/cli.py` — two new commands:

`crescendo models`
Lists all rows in `model_registry` ordered by `created_at DESC` in a tabular format. Example
output:
```
version              train_start  train_end   features  P@k    org_P@k  brier   ece
v0.3-lgbm-20260915   2026-05-01   2026-09-01  8         0.82   0.44     0.19    0.04
```

`crescendo reproduce <version>`
Looks up the row in `model_registry` for the given version string. Fetches the dataset rows
whose `as_of_date` falls within `training_window_start` to `training_window_end` from Neon.
Re-runs `crescendo build-dataset`, `crescendo train`, and `crescendo evaluate` with the same
config pinned at the registered training window. Uses `random_state=42` (always fixed) to
guarantee deterministic LightGBM splits. Writes a new registry row with version suffix
`-repro`.

## 9. Deployment checklist

These steps happen in order after all v2.0 code is reviewed, tested, and merged.

1. Merge `feature/v2.0-real-data-ml` → `develop` → `qa` → `main` via the standard PR ladder.
   Render auto-deploys both services on `main` push.

2. Verify both services are up: `curl https://crescendo-game.onrender.com/actuator/health`
   and `curl https://crescendo-predict.onrender.com/health`.

3. Manually trigger the `collect.yml` GitHub Actions workflow on `main`. This run executes
   `crescendo seed-genres` (idempotent — safe to run even if some artists already exist in
   `tracked_artist`) followed by `crescendo collect`. After this run, all 55 game artists
   are in Neon and have their first real snapshots.

4. Confirm via `crescendo status` against Neon: the latest `collect_run` row should show
   `status=ok` and `snapshots_written` equal to the game roster count (55 or the applicable
   count if some artists have been inactive).

5. Wait approximately 14 days. At that point, `crescendo build-dataset` can compute 7d and
   30d rolling features for the 55 game artists. Run it manually to verify the `dataset` table
   populates for those artists.

6. Flip the real momentum flag in the Render dashboard for `crescendo-game`:
   Set `CRESCENDO_GAME_USE_REAL_MOMENTUM=true`. Render will restart the service. No code
   change or redeploy is required.

7. Verify in the live game: open the draft board and confirm that momentum scores and
   prediction intervals reflect real collected data (the `dataset_version` in the API response
   will change from `synthetic-demo` to the real version string).

8. Wait approximately 45 days from the initial collect run (approximately mid-October 2026).
   At that point, 30-day forward labels are available. Run `crescendo train` and
   `crescendo evaluate` to produce a real-data model artifact. Deploy it to `crescendo-predict`
   by updating `MODEL_PATH` in the Render environment.

## 10. Risk and rollback

**Primary risk: insufficient data before flip.** The 14-day minimum for feature computation
is a soft floor — 30d features will be partial in the first two weeks. The risk is that the
game scores artists on noisy partial features, producing implausible rankings. Mitigation: run
`crescendo evaluate` before flipping the flag and verify that `organic_precision@k` is above
random baseline. If it is not, delay the flag flip until data is richer.

**Rollback procedure.** The real-momentum flag is a single environment variable. Rolling back
to synthetic momentum requires only one change in the Render dashboard:
`CRESCENDO_GAME_USE_REAL_MOMENTUM=false` (or removing the variable to use the default `false`).
The service restarts with synthetic scoring restored. No database migration or code rollback
is needed.

**Isolation Forest cold start.** For artists with fewer than 14 days of history, the old
heuristic inorganic detector is used automatically. This means the first two weeks of real
data will use the heuristic for the newly seeded 55 game artists. This is expected behavior,
not a failure mode.

**Multi-horizon model backward compatibility.** `CrescendoModel` (30d only) is preserved.
`MultiHorizonModel` is an additive class. The existing `/predict` API contract is extended
with new optional fields (`breakout_score_7d`, `breakout_score_14d`, `velocity_indicator`);
clients that ignore unknown fields are unaffected.
